# The archive (`supabase/`)

Everything the collectors gather lives in one Postgres table, `public.items`, in the club's Supabase project. The archive team owns this folder.

```
collectors/  --writes (service role key)-->  items table  --reads (anon key)-->  reader/
```

The schema is defined in [`migrations/0001_items.sql`](migrations/0001_items.sql).

## The `items` table

One row per collected item. Topics are a `tags` array, not separate tables, so one item can belong to several topics.

| Column | Type | What it holds |
| --- | --- | --- |
| `id` | bigint | Row number, assigned automatically |
| `source_id` | text, required | The source it came from. Matches `sources[].id` in `config/sources.yaml` |
| `url` | text, required | Link to the original. Every item must have one |
| `title` | text | Title as published by the source |
| `summary` | text | Text as published by the source. Never AI-written |
| `published_at` | timestamptz | When the source published it (can be empty) |
| `collected_at` | timestamptz | When our collector saved it. Filled in automatically |
| `tags` | text[] | Topic ids from `config/sources.yaml`, e.g. `{stablecoins,regulation}` |
| `raw` | jsonb | The original payload, so we can re-parse it later |
| `search` | tsvector | Full-text search index of `title` + `summary`. Generated by Postgres, never written directly |

**No duplicates.** `(source_id, url)` is unique. Collectors insert with "ignore duplicates", so running a collector twice in a day is harmless.

**Indexes** make three things fast: filtering by tag, full-text search, and sorting newest first by `published_at`.

## Who can read and write

Row level security (RLS) is on. With RLS, Postgres blocks everything unless a policy allows it, and the table has exactly one policy: anyone can read.

| Key | Used by | Read | Write |
| --- | --- | --- | --- |
| anon (public) key | `reader/` | yes | no |
| service role key | `collectors/` (daily workflow) | yes | yes, bypasses RLS |

The anon key ships to every browser that opens the Reader, which is why it must only be able to read. The service role key is secret and lives only in `.env` and GitHub Actions secrets.

When the anon key tries to write, inserts are rejected with an error. Updates and deletes do **not** error: RLS hides every row from them, so they match nothing and change nothing.

## Checking the table

[`scripts/check_items_table.py`](../scripts/check_items_table.py) saves a test item with the service role key, reads it back with the anon key, then confirms the anon key cannot insert, update, or delete.

1. Put `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_ANON_KEY` in the repo root `.env`. `SUPABASE_URL` is the bare project URL (`https://<project>.supabase.co`), without `/rest/v1` on the end.
2. From `collectors/` with `.venv` activated:
   ```bash
   python ../scripts/check_items_table.py
   ```
3. Every line should say `PASS`.

The script writes a test row (`source_id = 'archive-smoke-test'`), so run it against your own free Supabase project, never the club database: a test row there would show up on the live site. To check the club database, use `python ../scripts/check_items_table.py --read-only`. It only needs `SUPABASE_URL` and `SUPABASE_ANON_KEY`, confirms the anon key can read, and confirms there are no test rows. To set one up, create a project at supabase.com, paste `migrations/0001_items.sql` into its SQL Editor, and run it. It doesn't run in CI because it needs the network and real keys.

## Changing the schema

1. Never edit a migration that has already been applied. Add a new file with the next number, e.g. `migrations/0002_add_language.sql`.
2. Never write a migration that drops columns or deletes rows. The archive keeps everything.
3. Schema PRs need a lead's approval. Say in the PR that a lead must apply the migration to the club project, since merging doesn't run it.
